日期：2026-10-24。状态：三位独立审查者复核通过，18个设计问题条目已关闭；进入实施，代码和运行验收尚未完成。

## 1. 目标、授权与基线

依据薄荷记账 12.3.3 的本地静态分析和 542 组实采状态，独立实现接近其信息架构、视觉层级和已观察免费业务的 DawnYew。用户要求完整开发、编译验证及最终多 agent review，所有业务保持离线、免登录；会员/登录依赖内容仅保留空态入口。用户授权自主决策并留档，本方案以交叉审阅替代逐项向用户提问，不自行缩减为仅视觉原型。

参考资料：`.local/research/bohe-20261024/薄荷记账-完整功能与UI分析.md`、`round2/gallery.html`、同日三个审计文档。参考资源仅用于观察，不复制反编译源码、图标、图片或商业 SDK。原研究 APK、全部证据和手机上的测试样例保留。

工作树维持 `p/duanyao.0516/codex/dawnyew-android-app`。已有 `gradle.properties`、`gradle/gradle-daemon-jvm.properties`、`docs/implementation/ocr-release-jni-verification.json` 修改不覆盖。旧 2026-10-18 设计中“三页导航、不加资产”的范围被本次用户要求取代；金额、离线安全、草稿、事务、备份契约继续适用。

## 3. 架构选择

比较三种方式：直接改 EntryKind 加 TRANSFER 会触及已发布账单/退款/导入摘要、所有 SQL 与旧备份；把新财务数据写入 preferences/独立 JSON 会绕开事务、恢复和校验；选用**旧账单不变 + 同一领域中的新实体**。旧 Entry、Category 和旧九类备份记录形状不变，新功能通过有类型关系和只读统一投影接入。

责任边界：`shared:core` 负责金额、资金方向、计划执行、领域校验和统一查询语义；`shared:storage` 负责真实 Room 事务、迁移、SQL 与 payload 一致、流式导入导出；`shared:protocol` 负责 v1/v2 严格线协议；`shared:presentation` 管理稳定 operationId、内存草稿、返回栈、查询刷新；`shared:ui` 渲染与收集操作；`platform:android` 和 `androidApp` 保留 SAF、OCR、认证、代际授权，仅在平台确有职责时修改。

### 3.1 新增实体（全部可备份、同事务）

具体 Kotlin 构造签名在第一批实现中固定，并形成 `docs/implementation/2026-10-24-finance-api-contract.md` 供 UI/存储并行引用。公共原则如下：

- `Account`：账本、类型、名称、带符号初始余额、openingAt、archived、隐藏/计入资产、备注、排序、revision；八类统一手工资金账户。负余额表示负债，不再按账户类型反转第二次。余额起始默认当天 00:00:00，可在创建时选择更早日期；绑定的交易不得早于 openingAt，有引用后禁止改起始时间。编辑初始金额会重算全部余额，表单明确说明。隐藏仅影响默认列表，归档才禁止新增。
- `EntryDetails`：主键为 entryId，accountId、recorded、excludedFromBudget、reconciled、projectId、merchantId。不存在等价于无账户/已入账/计预算/未对账。`EntryTag` 以 entryId+tagId 关联，避免给严格标量 JSON codec 塞入未支持数组。
- `AccountTransfer`：单行原子描述来源/目标账户、金额、日期、备注、入账/对账、软删除、revision、创建/修改时间、关联业务类型及 ID。普通转账两端必须不同且同账本；明确的存钱进度转账可单端，不能两端都空。
- `Dimension`：PROJECT/MERCHANT/TAG，账本、名称、排序、归档、revision。已归档维度保留历史引用。
- `Contact`、`Obligation`：人员与借入/借出/报销单，包含可空 dueDate（未填不判到期），单据有专属应付/应收虚拟账户。Obligation.virtualAccountId 必须一对一，账户初始为 0、类型由单据固定。仅该单据命令能修改其资金：普通 Entry、普通转账、周期、存钱不能引用，普通账户编辑不能改其类型/初始余额/起始时间/资产计入；可在单据详情跳转查看流水。余额只由 active && recorded 的关联转账推导，不额外保存一套可漂移的“待还金额”。未入账本金/收付单列“待入账”，不增加可结算额；入账切换仍需同单据校验，不能超额。手工新建的普通应收/应付账户不自动成为单据虚拟账户。
- `RecurringPlan`、`RecurringOccurrence`：计划及每一期执行/跳过凭证；次数、原始日历锚点、下一索引、暂停/归档、revision；凭证唯一键 planId+index，保存生成账单/转账 ID。清理已生成交易不能使该期再生成。
- `SavingsPlan`、`SavingsMovement`、`SavingsWish`：目标及手动进度；前三种场景目标必填正金额，随手攒钱 targetMinor 可空表示无目标（不能用0）；金额用正数+存入/取出/愿望类型表达，进度只累计 movement，不能扣成负数。可选转账引用与进度变动同事务；无账户只影响计划，不影响资产。Wish.fulfilledMovementId 为完成事实，WISH movement 必须被恰好一个愿望引用，不另存独立 completed 标志；完成原子建立取出记录/转账，取消完成原子清理这些记录和引用。已完成愿望先取消完成才能改金额或删除，普通记录页不单独删除 WISH movement。
- `BudgetAllocation`、`BudgetReallocation`：既有月总预算下的分类额度与同月转移历史。allocation.amount 是当前额度唯一权威，历史不可变且不再次 SUM 到额度；撤回只能做检查当前可转额度的反向转移。子额度之和不超总额，转移前后总额守恒；下调总预算不能低于子额度和。分类被子额度引用时 DeleteCategory 拒绝，改为停用；有转移历史引用的子额度禁止独立删除，可随整个月预算明确删除。

所有新 ID 使用现有 UUID 校验；所有字符串沿用 NFC/长度/控制字符规则；金额以 Long 分计，单笔范围沿用 Money.MAX；汇总用溢出检查。所有更新带 expectedRevision，跨记录操作由 DomainEngine 一次发布。旧操作回执/导入摘要不重新授权旧修改记录。

### 3.2 金额与关联不变量

1. 收入 +amount、支出 −amount、退款 +amount 影响选中资金账户；仅 active 且 recorded 的交易影响余额。未入账仍在普通收支、预算和最近交易里出现。
2. 普通统计收入/支出只由 Entry 决定，转账从不进入普通收支；退款抵扣支出。预算额外排除 excludedFromBudget，退款动态读取父支出的预算排除状态，退款自身该字段固定 false、界面只读展示父项状态，避免复制漂移。退款按自身日期进入对应月份，允许月净支出为负，budgetUsed 对最终净额钳制到 0；总收支与预算消费使用独立字段，不能把排除预算误当排除统计。
3. 普通转账原子扣来源、加目标；两端都计资产时净资产不变。借入为应付→现金，偿还反向；借出/报销为现金→应收，收款反向。禁止超额结清和改变系统虚拟账户的初始余额。存钱可选转账同样严格按用户明确选择的 from→to 扣/加，单端另一侧显示“外部资金”，净资产变化为计入资产目标额减计入资产来源额；存钱进度变化独立为存入正/取出及愿望负。无端点不建转账。UI 不根据“存入”自动猜选账户方向。
4. 修改 Details/标签等必须同时递增 Entry.revision，使旧导入撤销检测可识别用户编辑。移动账本时拒绝残留跨账本关联，UI 显示原因或提供重新选择；退款账户可继承父项，但已保存退款必须明确保持/修改，不能静默搬移真实资金。
5. 原账单删除组继续管理支出+退款；新转账使用独立软删除字段，统一回收站只读投影。有关联计划/存钱/借还的交易通过业务命令操作，不能绕开来源单据破坏进度；彻底删除保留“已执行”凭证并明确断开已删除结果引用。
6. 归档阻止新增但保留历史；删除有引用账户/联系人/维度/计划要拒绝并提示归档。ClearAll、DeleteLedger、Purge、UndoImport、恢复完整覆盖新关系。SetBudget(null) 表示删除该账本月份整组预算配置，原子清理分类额度及转移历史，确认页说明范围，不影响交易。子预算转移仅同账本同月份且额度不为负，历史保留名称/引用的规则由 API 固定。

### 3.3 周期执行与时间

日期使用现有严格本地 ISO 日期/时间，金额记录不能未来发生。月/季/年计划由原始日锚点计算，如 1 月 31 日→2 月末→3 月 31 日；闰年与周末由日历计算。保存计划时处理到期首期；恢复前台后处理已到期项目，暂停不执行。每批最多 100 期，若超出则显示剩余待处理，下一次显式处理继续；不在主线程无限循环。一次执行只允许到期项，跳过推进索引但写凭证。持续计划用明确的无限标记，不能以溢出次数表达。错误计划显示阻塞原因，其余计划可继续；不会伪造成功。重启、重复触发、回执重试均不能重复生成。

nextIndex>0 后锚点/频率不可改；只改未来金额、分类、账户、备注和总次数（不得小于已处理次数）。要改频率，归档原计划后新建，保留旧凭证。凭证定义包含已跳过期次，总次数按已处理期计，显示“已生成/已跳过/剩余”避免混淆。

平台触发为统一“前台就绪”：resumed && !covered && authorized && !deviceLocked && repositoryReady，且没有待确认回执/外部 picker lease/正在提交的用户操作。覆盖无锁冷启动、普通返回、认证成功、合法 picker 返回、恢复后；不是只在认证回调执行。每次提交前重新核对 sessionEpoch、databaseEpoch 和前台条件，后台取消任务；旋转/重复事件仅重用单飞任务，不循环自动消化超过 100 期的积压。自动处理与手工命令共用 AppController 单写门；不得代用户确认未知 pending 回执。系统命令持有自己的 operationId，成功核验回执后只 acknowledge 自己的操作，再发布生成/跳过/失败摘要；结果未知或确认失败进入现有恢复提示，不继续写入。每期生成账单的 creationOperationId 使用独立期次 UUID，批操作另有外层回执 ID，不能一批多笔共用账单创建身份。

### 3.4 查询与 UI 状态

引入 `FinancialActivity` 只读投影合并 Entry+AccountTransfer，统一时间/ID排序；`ActivityScope` 包含 ledgerIds、startDate/endDate、kinds、categoryIds、金额上下界、accountIds、projectIds/merchantIds/tagIds、关键字、recorded/excludedFromBudget/reconciled 条件。分类选择只匹配 Entry（退款跟父分类），不会把无分类普通转账混入该下钻；未限定种类/分类时两种活动都出现。QueryScope→ActivityScope 转换完整保留旧种类/分类/日期/账本/关键字与归档条件。查询签名和游标绑定 datasetId/contentVersion/scope；数据修改或恢复使游标失效。生产列表实现 SQL keyset/union 或等价有边界的数据库查询，不以每页扫描完整历史替代现有分页。首页最近项、日历笔数、账户/往来/维度下钻消费同一语义。

普通统计保留现有 SQL 聚合/校验链，加预算排除 JOIN；统一资金投影单独计算账户/转账汇总。Activity identity 为 family(ENTRY/TRANSFER)+id，排序固定 occurrence DESC、family DESC、id DESC，游标包含三者；同 UUID 的不同实体也不串详情。首页月历仅取当前月份范围；图表不把数据缺失当零显示，加载/错误状态保留。转账的标签管理若无证据可省略，但列表必须正确表示其账户与业务来源，不能消失。

三张统计卡使用独立请求身份：分类和日趋势共享选中月 snapshot；月度收支单独请求选中年范围并按月聚合，不覆盖月结果。每张卡下钻保存自己的实际 query 和来源 route，返回不改其它卡范围。环图以原始支出形成非负份额，退款和净支出独立列出；仅退款月份显示退款与净额，不绘制负扇区或除零。加入不同月份与仅退款月测试。

所有编辑草稿只在进程内，稳定 operationId 自打开至确认保存；成功回执和 UI 确认沿用既有协议。切账本、恢复/清空、授权失效清理新草稿和筛选；不把凭据/URI/认证状态塞入 saveable。返回优先离开弹窗，再询问放弃脏草稿，再回来源页，保留来源筛选。

## 4. 持久化、备份与升级

- 数据库 3→4 只新增必要实体/索引/触发器，旧 Entry payload 不变。沿用 1→2→3→4 显式升级，升级发生在候选 generation 副本，检查后才发布，不 destructive migration。
- 新实体的索引列与 JSON payload 都要验证；FK、同账本、业务关联方向、唯一期次等通过数据库约束及领域/候选验证覆盖。不能只有开库时检查、恢复时跳过。
- `LedgerState`、`LedgerEntityBatch`、Rows、DAO 差量写入、Snapshot/Streaming、CandidateVerification 都覆盖相同实体集合。清理按子→父、写入按父→子；必要环状关系使用 deferred FK 并最后全量验证。
- 备份升级为 formatVersion=2，canonicalizationVersion 保持 1（规范化算法不改）。v2 精确包含新旧实体和字段集；v1 仍按原九类字段、计数、摘要严格验证，再显式提升为新实体为空的状态。禁止补字段后再算旧摘要，禁止将未知实体/字段静默忽略。PreparedBackup 保留 sourceFormatVersion/sourceCounts/sourceDigest 原始清单，单独提供 expectedCandidateCounts（v1新增实体补0）供当前库比较，不篡改来源 metadata。
- 新增宽整数字段列入协议字符串整数白名单；允许负号的初始余额使用独立 signed decimal string 规则。所有生产流式 JSON 编解码、规范存储、schema、恢复预览、加密包共享版本判定，不能只修内存 BackupProtocol。根字段乱序采用现有逐记录私有磁盘暂存、读完元信息后按版本验证实体集合及摘要；旧九类 record 格式不变，可边读边严格校验，再按源版本拒绝未知新实体。禁止完整根对象入内存；暂存始终受取消/空间/清理保护。大文件验收超过20MiB/10k记录。恢复日期只校验格式及领域关系，不依赖当前时钟拒绝历史文件里合法日期。
- v2 可恢复无新实体的旧账本；v1 fixture 要保存旧序列化后的真实字节和摘要。旧 ImportMember committedContentDigest 不变，用户编辑 Details 通过 Entry.revision 阻止误撤销。
- 新设置集中白名单和取值验证，命令/全量/批量恢复共用，必须有 UI 消费方。安全凭据不进入业务备份。

### 4.1 CSV v1 交换边界

CSV 仅交换有效的普通支出/收入，退款、回收站、转账、账户/项目/商家/标签及计划关系不在格式内；导出前列出选中范围、可导出笔数、排除笔数和内容。完整还原用 JSON/加密备份。一次导出/导入最多 10,000 条逻辑交易；10,001 条在预览/创建文件前明确拒绝，提示缩小日期范围或用完整备份，绝不截断或暗中多批提交。读文件最多 32MiB，每字段最多 8KiB 且最终仍服从领域长度。

首条格式记录为 `DawnYew CSV,1`，下一条固定表头 `source_dataset,source_entry,type,amount,occurred_at,ledger,category,note`。UTF-8 可带 BOM；RFC 风格双引号/双引号转义、CRLF/LF 和引号内换行；额外空记录拒绝（允许最终换行），列数/版本严格。type 仅 EXPENSE/INCOME、amount 正金额两位小数、occurred_at 严格秒时间；source_dataset/source_entry 为 UUID。自由文本 ledger/category/note 在文件中统一加一个前导单引号，v1 导入必须有该标记并且只去掉一个，原先以单引号/公式字符开头仍可逆；文件外的普通 CSV 不猜测这套规则。

业务 preview/mapping/commit 使用连续逻辑交易编号（格式和表头不计入），实际物理行范围只用于定位解析错误。扩展 DocumentFacts 增加可空 logicalRecordCount 和统一 previewRecordCount，保留 physicalRowCount 的原义及默认行为；旧 XLSX/测试不传新字段时仍用物理行。禁止把引号内换行补成虚假交易。导入目标为用户选定本地账本，分类按类型/规范化名称明确映射或预览新增，来源身份固定为 provider=DAWNYEW_CSV、scope=source_dataset、eventKind=type、externalId=source_entry，规范摘要覆盖解码后的业务字段。已有来源内容变化视为冲突，不覆盖；同源重复跳过，本机同ID已有记录须业务一致才可映射，疑似同日同额需明确确认。预览绑定 dataset/version/epoch，提交走既有单事务 ImportPlan 和撤销保护。

CSV 测试含逗号、引号、CRLF、引号内换行、BOM、空行、公式前缀、原单引号；9,999/10,000/10,001 记录边界、相同来源二次导入、冲突与 preview 过期。JSON v2 与加密 DWYBAK v1 envelope 独立：只更换封装内 JSON，不改 crypto profile/KDF/JNI/金向量。

## 5. 视觉、离线与平台约束

品牌 #00C4B3，浅底 #F2F5F9；白卡、轻边界、清楚的灰色辅助文案；支出粉色、收入青绿、转账蓝色。使用自有矢量/Compose 几何图标和渐变，不复制参考背景照片。暗色模式、200% 字体和 48dp 触控目标保留。关键入口有 contentDescription，不仅颜色表达种类。底部 Insets/IME/横屏须可滚动；金额计算器校验四则运算、括号、精度/除零/溢出，不用浮点解析金额。

最终 merged manifest 和 APK 不含 INTERNET/ACCESS_NETWORK_STATE，不新增 HTTP/云/广告/支付/语音云服务。既有本地 OCR 资源、SAF provider 白名单、FLAG_SECURE、后台遮盖、会话 lease、generation epoch、进程死亡失效保持。桌面组件及预览固定只提供静态图标和动作名称，通过显式本地 Intent 打开应用/记账；不含金额、账本名、交易摘要，不缓存敏感财务数据。入口必须先走现有锁定授权，Intent 只能请求导航，不能提交交易。

## 6. 实施与审阅门槛

1. 三个独立审查者交叉看整份方案：领域/备份、UI/覆盖、Android/构建安全。问题逐项留档；P0/P1/P2 必须关闭或通过更安全设计消除后才开发。
2. 先固定新模型/命令/查询 API；按 core、storage+protocol、UI 三个文件责任区并行，主 agent 负责 presentation/Android 整合和统一构建。禁止多个 agent 同时改共享文件或并发 Gradle/设备。
3. 对钱、周期、迁移/备份和生命周期写有意义的失败测试再实现；纯视觉不堆实现镜像测试。每批明确事实验证等级。
4. 集成后第二轮多 agent review 实际 diff、测试与最终 UI；相互审查其他责任区，修复并复查后交付。
