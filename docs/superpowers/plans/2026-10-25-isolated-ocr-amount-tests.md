# 独立截图金额识别测试计划

**目标：**用本地真实截图及文件名标注，单独验证当前随包模型的金额识别，区分模型错误、金额解析和支付场景门控；不启动记账应用、申请截屏权限或写账。

**方案：**在 `platform/android` 增加独立 instrumentation 测试APK，直接调用生产 `AndroidOfflineOcrEngine` 的随包ONNX模型、OpenCV、检测/裁切/识别流程。将现有 `ImageInputService` 中文件解码部分抽为共同的内部decoder，测试与选图使用相同尺寸、格式和软件Bitmap策略。测试脚本负责独立样本、期望结果、报告和清理，识别器只能看到图片。

**选择依据：**现有host smoke会重写部分预处理且使用生成文字，不作为这两张真实图的主验收。整App测试会夹入权限、会话、页面和数据库，本阶段不采用。独立Android库测试既复用真实推理又没有上述业务依赖的运行时动作。

## 文件职责

- `platform/android/src/main/kotlin/com/dawnyew/platform/files/ScreenshotImageDecoder.kt`：从受控文件校验/解码Bitmap，边界与原ImageInputService一致。
- `ImageInputService.kt`：继续承担URI来源校验、流式限量复制、摘要和暂存文件所有权，只调用共同decoder。
- `platform/android/src/androidTest/.../ocr/ScreenshotAmountRecognitionTest.kt`：仅图片推理与结果报告；先完成推理再加载期望金额比较，不接触Repository、MainActivity或保存命令。
- `platform/android/src/androidTest/.../files/ScreenshotImageDecoderTest.kt`：解码格式、尺寸、取消边界。
- `scripts/test-ocr-amounts.py`：从文件名取得严格小数标注，将样本以无金额的ID暂存/传入测试APK私有目录；构建/安装仅该库测试包，拉回报告并清理设备样本。
- `docs/implementation/2026-10-25-ocr-amount-baseline.md`：记录样本级结果、模型版本、测试设备和下一阶段门槛，全文OCR及图片仅在`.local`私有报告中。

## 验收与不越界

1. 文件名仅用于oracle，不传给模型/候选提取器，不根据答案裁剪或修正小数点。
2. 使用整张原图经生产解码/缩放；报告原尺寸、输入尺寸、SHA256、模型版本、每次耗时和原始OCR block（文字/置信度/框）。
3. 分别报告金额绝对值匹配、负号保留、候选及现有PaymentScreenshotParser结果。现有账本用正整数分，因此金额与支出方向分开核验。
4. 对每图重复运行，避免把“文本中碰巧出现答案”当成最终金额选择或模型泛化准确率。仅2张样本通过不代表所有支付截图通过。
5. 先记录真实基线。仅有模型/预处理错误证据才修改对应生产逻辑；场景门控问题记录到下一阶段，不为让金额测试通过绕过支付/入库限制。
6. 原始图不加入源码资源、APK assets或Git，不上传网络。测试报告私有目录不混入公开文档。所有临时设备样本及完整OCR报告在拉回后清理。
7. 保留当前分支和三个原有本机配置/历史报告改动；本阶段不提交推送。

## 用户纠正后的解析契约

用户明确指出主动截图不应再被渠道名、支付状态或导航文案拒绝。本阶段因此继续修改独立金额解析契约，替代上文“只记录场景门控、不修改”的原定范围：

- 去掉渠道、成功状态、状态次数、退款/收入/账单导航等页面业务门控。金额判定只依赖金额自身及消歧证据。
- 保留金额格式、数值范围、置信度和多金额不确定性；不猜小数点，不将不确定候选自动填为确定金额。无可用文字、模型资源上限仍是技术失败。
- 显式支持 `+`、`-`、`−` 与货币符号组合；金额字段继续使用正整数分幅值，原文符号仍保留在模型报告中，不据此推断收入/退款。
- 用测试先证明旧门控失败，再修改生产解析器；复跑两张真实图片，同时独立断言金额文本与最终解析幅值。
- 当前编辑器的支出默认值与退款关联不属于本阶段，不声称已完成类型识别或入库验证。

- [x] 更新解析单测并确认旧实现失败。

## 用户明确的正负号方向规则

用户进一步指定：正号收入，ASCII/Unicode 负号支出，没有正负号默认支出。本轮把方向从被选中的金额词元传到确认草稿，并按方向选择对应分类；金额仍为正整数分。符号不取自页面上其他金额，不根据渠道、支付状态或商户推断。候选金额或正负号冲突时保持待核对，不自动选择冲突的一方。

责任链为 `PaymentScreenshotParser` → `CaptureRecognizer` → `CaptureDraftUi` → `EditorDraft.create`，不新增数据库字段或写入路径。已有账单编辑和关联退款仍以原账单/原支出为准；人工改类型和保存前确认保持不变。

验证先覆盖解析与草稿的失败测试，再验证正/负/无符号、符号与所选金额绑定、分类匹配、人工确认及既有编辑/退款优先级，编译实际 Android App；真实两图只覆盖负号，不能代替正号截图样本或完整入库实测。

已完成，结果见 [离线 OCR 原理与正负号方向规则](../../implementation/2026-10-25-ocr-direction.md)：解析 31 项、presentation 131 项、标注 4 项通过，Android 编译成功；真实两图的金额与支出方向各 6/6 通过。独立审阅通过，完整 App 入库设备闭环仍未验收。
