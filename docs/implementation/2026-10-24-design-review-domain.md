复核结论：D1–D8 均已在修订方案/计划中形成明确规则，本审阅范围内无剩余 P1/P2 设计阻塞，可按冻结规则编制 API 并实现。独立扩展实体架构继续成立。以下保留初审发现及当时行号，末节列出逐项关闭依据；设计关闭不等于实现或测试通过。

## D1 [P1] 专属虚拟账户没有唯一所有权和普通命令禁写规则

位置：spec:45–49、60–63；plan:36–40。

触发：借入单生成专属应付账户后，用户从普通转账表单选择“现金→该应付账户”，不带 obligationId，或把普通收入直接记到该账户。现有描述只禁止绕过“有关联单据的交易”，没有禁止创建一笔无关联但使用该虚拟账户的新交易。这样单据可能按业务关联算剩余，而账户按全部交易算余额；如果单据直接用账户余额，又可绕过超额还款、结清和关联交易编辑保护。

必要决定：

- 明确手工创建的 RECEIVABLE/PAYABLE 与系统专属账户的区别；可采用 `systemOwnerType/systemOwnerId` 或 Obligation.accountId 的唯一约束，不用名称推断。
- 一单一个专属账户、一个专属账户只能属于一单、同账本、初始值固定 0；所有允许触达专属账户的活动必须携带并验证相同业务归属。
- 普通 SaveEntry/SaveFinancialEntry、普通 Transfer、周期模板和 SavingsMovement 的账户选择/领域校验均不得使用专属账户；账户编辑不能解除所有权或改初始值。
- 固定借还单“未入账本金/还款”的显示和可结算口径。当前账户余额排除 recorded=false，而“余额由关联转账推导”没有说明是否同样排除；应明确未入账列为待入账，不允许其虚增可还/可收额，或明确定义独立计划口径并用不同名称展示。

关闭验收：普通命令伪造使用专属账户、伪造别单 ID、一个账户关联两单、修改系统初始值都失败且整库不变；未入账借入及偿还的账户/本金/已还/剩余四个值有固定预期。

## D2 [P1] 退款预算排除的权威值没有冻结

位置：spec:46、59、61；plan:39、59。

触发：支出100、退款20，随后把父支出改为不计预算。EntryDetails 给每条流水保存 excludedFromBudget，方案说退款“继承父支出”，计划又要求预算 SQL JOIN Details/退款父项。若 core 取退款创建时复制值，SQL 动态取当前父项，二者会输出不同预算；若两边都读独立退款值，父项被排除后退款仍抵扣其他消费。

必要决定：推荐预算资格以当前父支出为唯一权威，退款预算排除不可独立编辑；core 与 SQL 统一使用 `effectiveBudgetExcluded(refund)=parent.excludedFromBudget`，类别仍沿用现有退款归属，退款金额按退款自身发生期间抵扣，最终 used=max(net,0)。EntryDetails 中退款同名字段要定义为不得产生独立含义（禁止矛盾值或明确定义不参与计算），不可一边存复制值一边动态查询。跨期、父项状态更新、软删/恢复时亦相同。

关闭验收：先退款后切父预算标志、跨月退款、退款单独软删/恢复、v2恢复包含矛盾字段时的处理，core/SQL/预算明细一致；普通收支金额不受预算标志影响。退款账户是另一项独立事实，预算继承不能顺带重写其账户或 recorded。

## D3 [P1] 单端存钱“转账”的资金语义未定义

位置：spec:47、51、58–60；plan:37、40、50。

触发：存钱5仅选付款现金账户时，单端 transfer 会让现金及净资产减少5，普通支出和预算不变；只选收款现金时，净资产增加5，普通收入不变；无账户时资产又完全不变。三个结果都可能合法，但方案只宣布单端可保存，没有说明资金去了何处、单端是否属于内部转账、取出时如何反向、界面如何解释净资产变化。参考仅实测双空账户，不能据“至少一账户有效时建交易”直接推出这套金额语义。

关闭方式二选一并留档：

1. 本轮限定同时选择两个账户或都不选，单端校验拒绝；这是明确的安全范围差异。
2. 保留单端，把缺失端明确建模为“未纳入管理的外部资金”，冻结 from-only/to-only 的方向、存入/取出的映射、对 netWorth 的变化与不计普通收支的原因，UI 标记为转出/转入管理范围；它不能与普通双端内部转账混同。领域与候选校验仅允许 Savings 业务生成单端，不能通过普通命令伪造。

关闭验收：存入/取出各覆盖双空、仅来源、仅目标、双账户、两端同账户；金额守恒或预期资产变化、进度变化及删除恢复均有明确金样例。

## D4 [P1] SavingsWish 与 WISH movement 可能重复或漏扣进度

位置：spec:27、51；plan:40、50、78。

触发：愿望100标记完成时，若进度同时减去 completed wishes 和 `SavingsMovement(type=WISH)` 就扣两次；若只切 completed 没有活动记录，编辑愿望金额或取消完成可能重写历史，却没有可追踪的进度变动。当前模型只给名称，没有完成、反悔、重复点击、完成后金额编辑及关联资金交易的状态契约。

必要决定：推荐 SavingsWish 是目标资料；“完成愿望”原子创建唯一对应 movement，进度只按 movement 计算，完成标志从有效完成 movement 推导或与其强一致。固定撤销完成是软删该 movement 并同步关联 transfer，重新完成创建新动作但不能保留两个有效完成记录。完成后编辑金额需经同一命令同时更新 movement（及 transfer）或明确拒绝。取出/愿望不能让存入净额变负；没有目标金额的“随手攒钱”用 null/明确无目标语义，不能用0绕过 Money 正金额规则。四场景的目标必填/可空应在 API 冻结前写清。

关闭验收：重复完成、取消后重做、改已完成愿望金额、删除关联资金交易、先删除存入导致已完成愿望超额，均不会重复扣减或产生负计划余额；备份恢复重复活动完成引用被拒绝。

## D5 [P2] 预算父记录删除与转移历史的权威关系缺失

位置：spec:26、52、63；plan:39–40、59。

触发：现有 `Command.SetBudget(..., amountMinor=null)` 删除 MonthlyBudget。新增 allocation/reallocation 后仍可从旧预算设置入口删除总预算；如果数据库有 FK 就变成未经定义的存储错误，若没有则留悬空子预算。原 `DeleteCategory` 仅检查 Entry 引用，分类只有 allocation 也可能被删除。另有 allocation 当前值与 reallocation 历史两份量，未说明历史是否再参与额度计算或能否修改/删除。

必要决定：选择“有子预算/转移历史则拒绝删除并指引先处理”或“明确级联删除预算计划及历史”，由领域命令执行而非依赖 SQL 抛错。补 `DeleteCategory`、旧 SetBudget 和账本删除关系。推荐 allocation.amount 为当前唯一额度，reallocation 是不可变审计记录；展示预算不能再次 SUM 历史。若允许撤销转移，用反向命令且检查当前额度，不直接删历史并倒算。

关闭验收：总额下调、删除总预算、删仅被子预算引用的分类、额度转移重试、转移后手工编辑再撤销、历史备份恢复；金额和记录均一致且无悬空引用。

## D6 [P2] 已执行周期修改频率/锚点后，index 不是稳定的日期身份

位置：spec:23、50、67；plan:47–48、78。

触发：月周期已执行 index0=1月31日，编辑成周周期或更改开始日后 nextIndex=1 的日期可能落在已执行日期以前，重新生成一个较早账单；若重置 index 为0又撞唯一键。方案保留“修改”功能但只规定历史流水不自动修改，没有固定哪些计划字段可修改、已执行次数如何计、跳过是否耗尽有限次数。

必要决定：第一版可在已有 occurrence 后冻结 frequency/anchor/start、只允许修改未来模板和次数/暂停；要换周期通过结束旧计划并新建。或者明确引入 scheduleRevision 及新锚点/索引映射，但必须定义不重生历史。建议有限次数按执行或跳过的期数消费；执行失败不写凭证、不推进。超期批处理一条外层 operationId 内生成的多笔 Entry 必须各有唯一 creationOperationId，并有稳定 occurrence 根关联。

关闭验收：已执行后修改周期、跳过最后一期、失败重试、修改总次数小于已消费期数、同一批多期的 creationOperationId 唯一、重启/备份恢复后不重复生成。

## D7 [P1] 前台自动周期处理没有接入现有 pending-operation 单写门

位置：spec:67、75；plan:76、87。现有源码：`platform/android/src/main/kotlin/com/dawnyew/platform/storage/GenerationRepository.kt:215` 之后的 execute；pending marker 在 UI acknowledge 前会阻止不同 operationId 的新命令。

触发：用户保存账单已提交但尚未确认回执，切后台再解锁。计划处理立即提交新操作会被 pending marker 阻止；如果为继续而自动 acknowledge 旧操作，就可能吞掉用户未确认结果。后台处理一次多期又可能生成自己的 pending marker，而没有匹配的 UI 结果确认入口，导致后续所有手工操作被“请先确认上次操作”阻塞。

必要决定：前台 executor 与普通编辑共用明确 coordinator：存在用户 pending recovery/正在提交时不启动；不能代用户确认未知 pending。系统周期命令使用持久 operationId，成功后由同一 coordinator 验证回执并完成自己的 acknowledge，再发布汇总；结果未知走恢复提示，失锁停止新增命令。多个到期任务不可独立调用仓库争夺 marker。主界面重新进入不能重复注册多个 executor。

关闭验收：手工提交成功但未确认时解锁、周期提交后 acknowledge 失败、周期中锁定、两个前台恢复事件、周期处理后普通保存；均不吞回执、不重复记账、不永久锁住写入口。

## D8 [P2] 严格流式协议必须冻结完整预览和候选计数的版本边界

位置：spec:82–84；plan:66–69。现有源码：`JsonStreamCodec.kt:52` 在 parse 前创建固定实体 stores，`:138` parse 边读边按固定 RecordSchema 验证；`GenerationRepository.kt:337` 后的 prepareRestore 直接比较 candidate counts 与 prepared metadata counts。

计划已经正确要求乱序根字段与 v1 先验摘要，但“从根对象暂存”有两种不等价实现：将整个根 JsonObject 放内存会退化已有大备份流式保证；直接把旧 metadata counts 改成新集合会失去“认证源清单”和“当前候选清单”的区别。应在设计/API contract 固定为有界逐记录或原始字节磁盘暂存，而非 dataset-wide JSON 树，并分离 `sourceFormatVersion/sourceCounts/sourceDigest` 与 `expectedCandidateCounts`。

推荐先私有暂存原始流、读元信息，再按已知版本流式解析/排序/验摘要；或保留已有逐记录 staging，完整根元信息后逐批按对应 schema 验证。v1 空新表的0计数只用于候选预期，不改原清单，不跳过候选差异检查。所有暂存仍受取消/空间/清理约束，解密流进入同一流程。

关闭验收：entities 在 version 前的旧大文件（超过20MiB/10k条）保持有界处理；来源摘要正确但未知新字段的v1拒绝；恢复预览不污染当前库；映射漏表/多条新实体时 counts 不匹配拒绝；新 v2 加密恢复走相同链。

## 非阻塞观察与范围确认

- 不改变旧九类 record 形状，可以避免当前 Rows.from 的严格重编码判损坏；这部分决策正确。新命令另建类型、复用内部 helper 的方案也已避免递归 apply 多版本/多回执。
- 当前 SQL/内存的预算口径必须分开普通统计；plan 已要求两端交叉金样例。新 Activity 分页的 type 排序 tie-breaker 应写入 API contract，严格 keyset 不应由 UI 拼两页替代。
- CSV 明确仅普通收支交换、完整关系走 v2，避免假称全量导出的方向正确；实现前还需按 Task6 冻结 CSV 列及损失提示，不应在本次 JSON 扩展中临时混入导入身份新规则。
- 会员/登录/网络占位、无 INTERNET、保留已有本地 OCR/锁/备份、稳定授权 epoch 都有明确边界，未见域模型审阅范围内的冲突。UI 和 Android 专题仍由其他审查者独立判断。

以上为初审设计缺口，不代表已发现运行中的新代码缺陷。当前没有实施或测试通过结论。

### 单端存钱的确定性验收样例

设金额5，账户A/B均计入资产；账户变化只在对应transfer有效且recorded=true时生效。取出/愿望案例先准备不少于5的计划余额。

| 用户选择 | 存入时计划变化 | 取出/愿望时计划变化 | 有效已入账时账户变化 | 净资产变化 |
| --- | --- | --- | --- | --- |
| 无来源、无目标 | +5 | −5 | 不创建transfer | 0 |
| A→外部资金 | +5 | −5 | A−5 | −5 |
| 外部资金→B | +5 | −5 | B+5 | +5 |
| A→B | +5 | −5 | A−5，B+5 | 0 |

同账户双端必须拒绝；任一已选账户不计资产时，净资产按spec:60的 `included(to)×5−included(from)×5` 计算，账户自身变化不受included设置影响。recorded=false时账户及净资产变化为0，计划movement仍按动作变动；删除/恢复须沿spec:62的业务命令原子联动。该矩阵是本轮自主设计的可验证口径，不宣称参考APP已实测所有这些组合。

实施验收继续执行各初审条目的失败场景，尤其虚拟账户伪造引用、父项预算切换、愿望重复完成、预算旧入口删除、用户pending期间自动执行及乱序旧大备份。后续发现代码偏离上述规则仍应作为代码问题修复，不因本次设计关闭跳过检查。
