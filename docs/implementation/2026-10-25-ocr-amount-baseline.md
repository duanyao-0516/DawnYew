# 独立截图金额识别初始基线

本文件保留移除旧业务门控前的测试结果。用户随后明确要求取消这些业务限制，最新实现与复测结果见 [主动识图的金额解析契约修正](2026-10-25-user-triggered-amount-parsing.md)。以下“当前业务解析器”均指本次初始基线使用的 `payment-screenshot-1`。

日期：2026-10-25。范围：只验证真实截图经过生产解码和离线 OCR 后，是否读出正确金额；不启动主应用，不申请截屏权限，不创建或保存账单。

## 结果

两张原图各运行三次，六次均在原始 OCR 文本中准确读出金额，包括负号和两位小数。当前业务解析器对两张图均返回 `UNSUPPORTED`。因此，本次证明这两张图的金额字符能够被模型读出，尚未证明业务能够正确选择最终金额或完成记账。

| 本地样本 | 匿名 ID | 模型原始金额文本 | 精确匹配 | 金额文字块置信分数 | OCR 调用耗时（按轮次） |
| --- | --- | --- | --- | --- | --- |
| `-1.98.jpeg` | `case-001` | `-1.98` | 3/3 | 0.999167 | 733 / 399 / 404 ms |
| `-35.50.jpeg` | `case-002` | `-35.50` | 3/3 | 0.997092 | 436 / 428 / 425 ms |

分数是识别器对文字块的输出，不是经过校准的正确率。首个调用为冷调用；耗时只统计 `engine.recognize(bitmap)`，不包含 APK 安装、文件传输和图片解码，也不能代表实体手机性能。重复运行用于观察同一输入的稳定性，不是六张独立样本。

报告摘要：`sampleCount=2`、`runs=6`、`exactSignedTokenMatches=6`、`magnitudeTokenMatches=6`、`businessParserResolved=0`。

## 实际使用的链路

1. 主机读取文件名的严格两位小数标注，用整数分保存期望值。
2. 传入独立测试 APK 的图片仅命名为 `case-001.image` 等匿名 ID；输入清单只有 ID 和 SHA256。
3. 图片经过生产共用的 `ScreenshotImageDecoder`。两张原图均为 1080 × 2351，实际模型入口 Bitmap 为 882 × 1920。
4. 直接调用生产 `AndroidOfflineOcrEngine`，运行随包检测、裁切和识别模型；没有 mock、人工填写 OCR、按答案裁剪或修正数字。
5. 保存原始文字块、坐标和置信分数；额外枚举数字文本，并运行现有 `PaymentScreenshotParser` 作为独立诊断。
6. 全部推理及候选枚举完成后才加载期望金额比较。比较逻辑不参与识别。

模型版本：`ppocr-v5-mobile/ort-1.31.0-cpu-no-telemetry/bgr-1`。业务解析器版本：`payment-screenshot-1`。测试运行于 Android 36 ARM64 模拟器 `DawnYewValidationApi36`（本次 serial 为 `emulator-5554`）。实体 OPPO 手机被系统锁屏挡住测试包安装，未完成实体手机推理验证。

独立库测试包为 `com.dawnyew.platform.test`，没有主应用 Activity、账本 Repository 的启动调用或 `INTERNET` 权限。生产模型权重与业务解析规则均未修改；生产代码仅将原有图片解码提取为共用内部组件，URI 校验、文件限额、摘要和暂存文件管理继续由 `ImageInputService` 负责。

## 暴露出的业务解析问题

| 样本 | 当前拒绝原因 | 代码与截图证据 |
| --- | --- | --- |
| `-1.98.jpeg` | 被归入不支持的支付场景 | 详情页的导航文字“全部账单”命中全页 `unsafe` 正则，提前返回。另一个待处理点是“自动扣款成功”不在现有成功状态白名单中。 |
| `-35.50.jpeg` | 缺少支持渠道的明确证据 | OCR 已读出“支付成功”，但现有渠道规则要求出现“微信”或“支付宝”；该页使用“财付通”标识，因此被拒绝。 |

这两个拒绝发生在金额读取规则之前，不能归因于本轮模型没有读到金额。本阶段记录原因，不通过放宽规则或强行生成账单来使测试通过。

## 重复运行

连接一台可安装测试包的 Android 设备，或先启动 Android ARM64 模拟器，再执行：

```sh
python3 scripts/test-ocr-amounts.py \
  --input-dir /path/to/labeled-screenshots \
  --serial emulator-5554 \
  --repeats 3
```

`--serial` 必须对应实际设备；仅一台设备连接时可以省略。脚本默认离线构建 `:platform:android:assembleDebugAndroidTest` 并安装独立库测试包，不安装记账主应用。`--skip-build` 仅用于复用已有测试 APK，报告会记录没有重新构建。Gradle 依赖须已缓存，否则离线构建会明确失败。

样本目录支持 1–32 张 PNG/JPEG，文件名必须是严格两位小数金额，例如 `-1.98.jpeg`；无法确定标注的文件会使测试失败。推理次数可选 1–5。脚本的成功退出要求设备测试成功且全部轮次含精确带符号金额文本；业务解析结果单独统计，不作为此阶段的通过条件。

每次运行生成 `.local/ocr-amount-tests/<runId>/`，包括构建/安装/运行日志、APK SHA256、基线 Git HEAD、文件标签、匿名样本与完整 `report.json`。Git HEAD 仅描述基线提交；本轮测试代码是工作区新增内容，不能将 HEAD 当作被测代码的完整版本标识，APK SHA256 对应实际运行产物。

原图与完整 OCR 文本不进入源码、APK assets 或 Git。主机报告目录权限为 0700；设备私有样本及报告在拉回后清理，异常退出也先停止独立测试进程再尝试清理，清理失败会明确报错。

## 下一阶段的门槛

本轮仅两张样本，不能宣称泛化准确率达标；数字枚举中存在期望值也不等于已选定唯一的交易金额。接入截图到入库流程前，应继续在独立测试中完成以下事项：

1. 明确金额选择、支出方向和支付场景判断的独立契约，处理上述详情页导航与渠道识别问题。
2. 扩大样本集，至少覆盖多金额（实付/优惠/余额）、自动扣款、退款/失败、收入和模糊截图，检验错误接受及错误拒绝。
3. 为“最终选定金额”增加独立断言；未确定、多候选或不支持场景必须保持显式结果。
4. 在实体手机验证后，再接入用户核对与保存流程，并单独检查取消、重复保存和数据一致性。

本轮没有改动上述业务策略或入库流程，也没有执行新的 Git 提交或推送。
