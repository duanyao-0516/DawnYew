# 离线 OCR 原理与正负号方向规则

日期：2026-10-25。用户明确要求：金额前有正号识别为收入，负号为支出，没有正负号默认支出。本次将方向传到确认草稿并匹配对应分类，继续保留用户修改与确认保存。

## 当前技术链路

截图经生产解码与缩放后，由随包的 PP-OCRv5 mobile 两个 ONNX 模型处理：

1. `det` 文字检测模型定位文字区域，权重约 4.60 MiB。
2. OpenCV 按文字框裁切/校正图片，`rec` 文字识别模型输出文字，权重约 15.77 MiB。
3. ONNX Runtime 1.31.0 在设备 CPU 执行推理；结果包含文字、位置和置信分数。
4. 本地 `PaymentScreenshotParser` 从识别文字中选取金额并解析方向，再传到确认草稿。

模型文件合计约 20.37 MiB，不含推理运行库和其他 App 资源。版本、来源和文件摘要记录于 `platform/android/src/main/assets/ocr/manifest.json`。模型随 App 安装，不需要下载模型或上传图片，不使用云端大语言模型识别。

## 方向契约

| 被选中金额的原文 | 金额字段 | 预选方向 |
| --- | --- | --- |
| `+12.34`、`￥+12.34`、`+￥12.34` | 1234 分 | 收入 |
| `-12.34`、`−12.34`、`￥-12.34` | 1234 分 | 支出 |
| `12.34`、`￥12.34` | 1234 分 | 支出（用户指定默认值） |

方向来自同一个被选中的金额词元，不扫描整页寻找正负号；优惠、余额等其他金额不会改变所选金额的方向。金额保持正整数分，方向独立传递。没有根据“收入/退款”等页面文字新增推断或拒绝规则。

低置信度、多金额或相同金额正负方向冲突时，金额和方向均保持未确定并提示人工核对。原有确认与保存动作保持不变，不新增业务限制。

## 代码责任

- `PaymentScreenshotParser` 升级为 `payment-screenshot-3`，候选同时包含金额幅值和方向，按二者共同消歧。
- `CaptureRecognizer` 将方向传入进程内 `CaptureDraftUi`；不涉及数据库 schema 或持久数据迁移。
- `EditorDraft.create` 为新识别草稿设置收入/支出，并选择当前账本中对应方向的启用分类；无收入分类时不借用支出分类。
- 编辑已有账单、从已有支出发起关联退款仍以原账单类型和分类为准。用户在编辑器手动改变类型的逻辑未变。

本阶段之前的 [解析契约修正](2026-10-25-user-triggered-amount-parsing.md) 保留历史结果；其中“尚未判断方向、所有新草稿默认支出”的状态由本次实现替代。
