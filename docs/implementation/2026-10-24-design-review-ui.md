本次只读业务源码、方案和本地参考材料，仅写本文档；未运行编译/ADB。初审提出 3 个 P1、4 个 P2；随后已逐项核对修订方案（123 行）、计划（110 行）及关闭记录。**复核结论：UI-R1～UI-R7 均已在设计层关闭，无剩余 P1/P2；UI/用户闭环方向通过设计门槛。** 下文保留初审发现与关闭条件，末节记录实际修订依据。此结论不代替 API、实现、编译或设备验证。

## UI-R1 · P1 · 统一 ActivityScope 缺少分类过滤，默认环图下钻无法完整表达

位置：方案 `:20`、`:22`、`:71`；计划 `:36`、`:49`、`:59`、`:75`。

方案要求流水支持分类筛选，默认分类统计可下钻，但新 `ActivityScope` 字段集列了账本、日期、种类、金额、账户、维度、关键字和状态，遗漏 `categoryIds`；计划又要求它与旧 `QueryScope` 分离。现有分类过滤在 `shared/core/src/commonMain/kotlin/com/dawnyew/core/Statistics.kt:5-7` 的 `QueryScope.categoryIds`，旧 `drillScope()` 也是通过该字段下钻，不会自动转移到新投影。

触发：本月餐饮和购物均有交易，点分类环图“餐饮”，随后在统一流水查看；若只复制日期和种类，新列表会出现购物交易。若在 UI 过滤已加载页面，则分页笔数/日汇总/下一页都不再正确。

建议：在方案中明确 `ActivityScope.categoryIds`（普通收支/退款分类）及其 AND/OR 组合规则；普通分类过滤应排除无法匹配此分类的转账，不能把项目 `Dimension` 当分类。固定 `QueryScope ↔ ActivityScope` 的纯映射方法和来源 scope；新增“同日期两分类+转账，类别下钻仅返回匹配活动、分页/汇总一致、返回保留原统计范围”的契约测试。若未来转账也有分类，使用独立类型/ID，不修改旧 Category 线格式来硬塞 Direction。

关闭条件：方案/计划和 API contract 都能明确表达上述查询；不依赖 Composable 二次过滤。

## UI-R2 · P1 · 账户模型缺少余额起始和归档字段，与引用的审计/验收相冲突

位置：方案 `:21`、`:45`、`:58`、`:63`、`:103`；计划 `:37`、`:78`。

`Account` 只列初始余额、隐藏/计资产等，没有 `openingAt` 或 `archived`。但同日领域审计第 4.1 节明确提出余额只累积 `occurrence >= openingAt` 的变动；本方案将该审计列为依据，且计划要求账户归档/引用测试，最终验收要求账户“新增→详情→编辑→归档/删除”。隐藏账户与归档账户不是一个状态：隐藏仍可被使用且应计资产，归档按方案 `:63` 阻止新增。

触发：用户新建余额 1000 的账户后，把上个月一笔支出指定到该账户。缺起始时间时实现者可得 987.66 或 1000 两个不同答案；重设初始余额后更容易重复计算历史。缺 archived 字段时 UI 无法兑现账户归档，而若偷用 hidden 会错误阻止隐藏账户记账或改变资产。

建议：Account 补 `openingAt`（含起始秒边界）和 `archived`，明确更新初始余额/起始时间会重算哪些流水；当前所有余额视图与账目迁移使用同一公式。或者选择“期初在全部关联历史之前”的更窄规则，但必须同时删掉/覆盖起始时间参考承诺，并在账户表单明确其语义；不能让 UI/SQL 各自解释。`hidden` 独立于 `archived`，隐藏账户仍计入资产，归档仍保留余额和历史、只禁止新增关联。

关闭条件：模型、表单、余额公式、归档限制与验收示例一致，覆盖起始前/起始秒/起始后、隐藏/归档四类情况。

## UI-R3 · P1 · 存钱允许单端转账但没有方向契约，已选择的安全边界尚未统一

位置：方案 `:27`、`:47`、`:51`、`:60`；计划 `:40`、`:50`。

方案允许“明确的存钱进度转账可单端”，却未定义存入/取出时单端是付款还是收款、与账户增减/净资产的关系；同日领域审计第 4.3 节明确建议本轮拒绝仅选一个账户，因为参考只实测双空，单端方向缺实测。两个文档给 UI 的校验政策相反。

触发：用户“存入5”只选现金；UI 若把现金当目标会 +5，把现金当来源会 −5。进度两者都 +5；金样例（只覆盖无账户）无法暴露错误。取出、编辑或删除这笔记录会进一步混淆资金和计划联动。

建议采用更安全的已提出方案：本轮存入/取出只允许“两端都空→仅计划进度”或“两端均选且不同→确定方向的一笔真实转账”；一端为空时表单明确要求补齐或全清空，并在领域再次拒绝。存入时来源/目标、取出时来源/目标由表单字段直接表达，不隐式交换。若总集成最终仍决定允许单端，则先写每种存入/取出×fromOnly/toOnly 的余额变化表，并据此测试，不宣称它来自已实测行为。

关闭条件：方案、审计决议、领域校验和 UI 输入规则统一；无账户进度不会创建两端空的 AccountTransfer。

## UI-R4 · P2 · 三张默认统计卡的范围未拆开，当前一套 snapshot 无法同时正确展示

位置：方案 `:22`、`:69-75`；计划 `:75`、`:77`。

参考三卡分别为“分类统计：选中月”“日趋势：选中月”“月度收支：选中年”；目前 `Statistics.calculate()` 在范围≤90天时产生日点，否则产月点（`shared/core/.../Statistics.kt:31-38`），`AppController` 的统计页只有一个统计结果槽。计划只写 facade 的“当前 dataset/scope”，没有明确三卡是否各自查询和下钻范围。

触发：全部套用当前月 snapshot 时，月度收支会变成每日柱图或只剩一个月；全部改用年度查询时，分类卡/日趋势将错误统计整年。点击月柱后若改了全局月范围，还会让另外两卡被动切换并破坏返回上下文。

建议写入三个独立结果槽/请求身份：选中月分类、选中月日趋势、选中年逐月聚合；允许其中两者共享同一月 snapshot，但不能让年度请求覆盖月结果。下钻保存该卡实际 query scope 及 source route，返回恢复原月/年。环图按**原始支出**作非负份额分母，退款和净支出另列；本月只有退款时显示可核对退款/负净支出，不生成负扇区或用 0 分母。这个规则保留现有 `categoryFinancialRows()` 与净支出语义，不新增参考未知算法。

关闭条件：API contract、controller 任务与测试包含“不同月份数据+只有退款月”的三卡范围/下钻案例。

## UI-R5 · P2 · 占位页仍展示具体说明，与本轮“仅留空占位无具体内容”不一致

位置：方案 `:17`、`:33`；计划 `:79`。

方案 `:33` 统一显示“参考功能依赖会员/登录或网络；当前离线版未提供”。用户要求会员/登录依赖入口只留空占位、无具体内容，审计中也明确为仅标题和返回。此处不需要增加解释性产品页；也不能用同一原因覆盖未经验证的免费能力。

建议：占位只有入口外观以及目标页标题/返回，内容区空；不展示会员权益、登录说明、不可用营销文案。受限原因放开发覆盖矩阵/本次交付文档。联网附属入口若采用相同空页也统一记录。开发完成度必须分“可用、明确受限占位、未完成”，不要把后者标成会员限制。

关闭条件：统一 Placeholder 页面契约改成空内容，并与二十入口范围表一致。

## UI-R6 · P2 · Widget 的金额条件仍留下实现分叉，需固化最新的无金额决策

位置：方案 `:31`、`:91`；计划 `:86`。

计划 `:86` 已定 Widget 不存金额，主 agent 本轮明确“本地 Widget 选快捷入口、无敏感金额”。但方案范围表仍说“金额展示遵守锁定策略”，`:91` 又写“若金额预览不能证明锁定安全，则只提供快捷方式”，会让 UI 或 Android agent 认为可再实现带金额分支。

建议直接固定：Widget 和预览都只显示自有静态图标、应用/动作名称，无金额、账本名称、交易摘要或其它本地财务数据；点击显式本地 Intent，经过已有锁定授权再打开指定动作。不要求本轮做其它金额 Widget，此为安全优先且已自主决议的范围边界，不属于未实测算法的遗漏。

关闭条件：范围表、平台章节、任务与验收统一无金额，不保留“若不能证明”的双分支。

## UI-R7 · P2 · “到期往来提醒”缺少到期字段，可用范围需澄清

位置：方案 `:29`、`:49`；计划 `:50`、`:78`。

设置承诺“本地提醒列表聚合到期计划/往来”，但 Obligation 只规定人员、单据和专属应收/应付账户，既无到期日期，也未在新增/编辑表单或命令中提供。只凭未结清金额不能判断“到期”；若把全部往来称为到期，会制造错误提醒。

建议选择其一并写明：为借入/借出单增加可空的 dueDate（用户手动设置，未设不进到期列表）；或本轮只展示计划到期提醒，往来在提醒页另区显示“未结清”，不声称已到期。无需新增系统通知/后台定时，也无需猜测参考贷款规则。

关闭条件：提醒标题、数据来源和表单/模型同一语义；未设日期不能显示逾期。

## 已核对且不阻塞的设计

- 保留旧 Entry / Category 线格式、增加同事务伴随实体并统一 FinancialActivity 是合理责任划分。CSV 限标准普通收支、完整关系走 JSON/v2 是明确可交付边界；导出页必须列明排除项与笔数，不能冒称完整财务备份。
- 统计 17 项的“启用开关/拖动”和配置保存有静态会员判断，见 `.local/research/bohe-20261024/evidence/round2-static-home-account-stat.md`“统计二级页面”表。因此本审阅不要求强做其它未实测统计算法或收费统计编辑器；需在覆盖矩阵引用这个证据。
- 当前 DomainEngine 已限制新交易发生时间不晚于本机现在（`Domain.kt:68-70`），并允许原未来记录保持原日期编辑（`:135`）；方案沿用这一写入约束合理。恢复验证仍必须保持与当前时间无关（`Validation.kt:20`），不要把“未来写入拒绝”扩散到历史文件恢复。
- 样例现金 1062.66、储蓄 20、应收 10、应付 −8、净资产 1084.66 与普通支出 16.34、预算剩余 283.66 在给定交易下可以核对一致。
- 返回栈、脏草稿确认、来源筛选保持、scope/version 游标失效、旧结果不能触发错误下钻是正确方向；实现 review 仍需验证具体路由与 stale 状态，不把计划文字当运行证据。
- 本轮 Widget 限快捷入口是明确接受的安全取舍；不以本审计此前较广的 Widget 建议反向覆盖总集成的新决策。
